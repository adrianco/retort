## Data flow

```
data/kaggle/*.csv
   │  (_load_brasileirao / _brazilian_cup / _libertadores /
   │   _extended_statistics / _historical_brasileirao / _players)
   ▼
SoccerRepository
   ├─ raw self.matches (23,954 rows) ─── _select_primary_matches / _deduplicated_matches
   │                                        ▼
   │                                     self._primary_matches (default query surface)
   ├─ normalize_team_name / canonical_competition / parse_match_datetime
   └─ query API: search_matches, team_statistics, head_to_head, search_players,
        competition_standings, team_leaderboard, analyze_statistics,
        competition_matches_by_stage, team_profile, knowledge_graph, source_summary
   ▼
NaturalLanguageQueryService.ask  (intent routing + follow-up context)
   ▼
BrazilianSoccerMCPServer  (initialize / ping / tools/list / tools/call)
   ├─ structuredContent = full repository result   ← complete & correct
   └─ content[].text = _human_readable_result(...)  ← lossy projection (see findings)
```

## Key design points

- **Overlap handling:** the five match CSVs intentionally overlap; the repo keeps
  a raw set (23,954) and derives a de-duplicated `_primary_matches` set used by
  default, so `competition_standings("Brasileirão", 2019)` correctly yields 380
  matches, Flamengo 90 pts (verified by `test_...benchmark_order_is_reproduced`).
- **Normalization:** accent folding + state-suffix handling keeps `São Paulo-SP`
  and `Sao Paulo` equal while keeping `Botafogo-RJ` ≠ `Botafogo-PB`.
- **Transport:** MCP is implemented directly over JSON-RPC (no `mcp` SDK) — the
  module docstring cites an incompatible local `mcp`/Pydantic install. Protocol
  negotiation, `tools/list`, `tools/call`, and error codes are all covered by tests.
